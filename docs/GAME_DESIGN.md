# 游戏设计

## 目标

Mansion Protocol 的目标不是复刻一个纯 UI 演示，而是提供一个可持续扩展的、以后端权威规则驱动的桌游框架。当前设计聚焦三件事：

- 探索阶段要稳定、可重复扩展
- 作祟与剧本阶段要支持主题化内容替换
- 数据层要逐步从硬编码迁到配置层，减少“改文案即改规则”的脆弱耦合

## 核心体验

### 1. 探索

- 玩家轮流移动并放置地块
- 地块可以通过 onEnter、onLeave、interact 触发规则
- 事件、物品、预兆通过统一的后端抽牌与结算路径推进

### 2. 作祟

- 预兆揭示后立即由后端发起作祟检定
- 作祟失败后进入剧本揭晓与阵营分化
- 前端只展示后端同步的阶段与揭晓结果，不本地推演

### 3. 作祟后对局

- 剧本目标与胜负判定由后端推进
- 战斗、状态、日志和目标更新都要通过统一状态同步回写

## 当前设计边界

### 已收口到配置层的内容

- 地块 enter / leave / interact 规则
- 奖励池与锻造产物
- 命名位置别名
- 技能树节点的结构化 grantsEffects
- GIVE_ITEM / GIVE_SKILL 的显式目标字段

### 仍在逐步迁移的内容

- passiveEffects 的结构化表达
- 部分状态效果和系统叙事模板
- 剧本特例参数与目标规则的配置化
- raw_data 到运行时产物的单一事实源治理

## 内容设计原则

### 可读

- 名称、描述和规则效果必须能从数据直接读出意图
- 同类内容应使用统一字段，而不是临时借用 message、description 之类通用文本字段承载规则

### 可验证

- 每类配置都应能在加载时被校验
- 引用不存在的卡牌、技能、位置、剧本应视为配置错误，而不是默默 fallback

### 可扩展

- 新能力优先走结构化 schema
- 若短期必须保留兼容字段，应在文档中标出“仅兼容，不再新增”

## 当前主题策略

- original 作为基础主题与验证基线
- volantis 作为扩展主题与复杂能力实验场
- 所有新能力优先在不破坏 original 基线的前提下扩到主题层
